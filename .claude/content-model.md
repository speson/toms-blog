# Tom's Blog Content Model (콘텐츠 모델)

> 이 문서는 "글을 어떤 형태로 만들 것인가"를 정의합니다. 말투/포맷은 `writing-style.md`,
> 발행 절차는 `commands/publish.md`·`commands/write.md`가 다룹니다. 세 문서는 함께 적용됩니다.

## 핵심 원칙 (가장 중요)

<strong>글의 단위는 "기사"가 아니라 "내 관점"이다.</strong>

- ❌ 기사 1개 → 번역·요약 포스트 1개 (출처의 구조를 그대로 따라감 = 2차 가공)
- ✅ 기사 N개 → 내 주장·질문·프레임 1개 (기사는 그 주장을 뒷받침하는 근거·인용)

출처(뉴스/릴리스)는 <strong>재료이자 근거</strong>일 뿐, 글의 척추는 Tom의 해석이어야 합니다.

### 가치 테스트 (모든 글이 통과해야 함)

발행 전 두 질문에 "예"라고 답할 수 있어야 합니다.

1. <strong>출처를 안 읽은 독자</strong>가 이 글에서 출처 요약 이상의 무엇(해석·맥락·판단)을 얻는가?
2. <strong>출처를 이미 읽은 독자</strong>에게도 새로운 관점·연결·결론이 있는가?

둘 중 하나라도 "아니오"라면 그건 2차 가공입니다. 각도를 다시 잡거나, 다이제스트로 묶거나, 발행하지 마세요.

## 글의 단위를 정하는 절차 (angle-first)

뉴스를 받으면 곧바로 쓰지 말고, 먼저 <strong>각도(angle)</strong>를 한 줄로 적습니다.

```
오늘의 재료: [선택된 뉴스 N건]
→ 이걸 관통하는 내 한 줄 주장/질문은? : "________"
→ 어떤 모델로? (칼럼 / 다이제스트 / 비교)
→ 근거로 인용할 출처: [A, B, C] + 블로그 기존 글 [내부링크]
→ 결론(독자가 얻어갈 것): "________"
```

이 한 줄 주장이 안 나오면 글감이 약한 것입니다. 묶거나 보류하세요.

### 뉴스 → 글 매핑 (1:1 금지, 티어로 판단)

| 상황                                             | 처리                                                                                                |
| ------------------------------------------------ | --------------------------------------------------------------------------------------------------- |
| 대형 단독 사건 (메이저 모델 출시, 인수, 상장 등) | 단독 글 — 단, "발표 내용"이 아니라 <strong>"그래서 무엇이 중요한가/어떻게 읽을까"</strong>를 척추로 |
| 서로 연결되는 소식 2~4건                         | <strong>하나의 종합/칼럼</strong>으로 묶어 트렌드·흐름을 그림                                       |
| 같은 주제가 여러 번 쌓임                         | <strong>비교/평가 프레임워크</strong> 또는 정기 다이제스트                                          |
| 사소한 패치·릴리스                               | 단독 발행 금지 → 정기 릴리스 다이제스트로, 또는 생략                                                |

## 3가지 기본 모델

### 1. 관점/주장 칼럼 (thesis column) — 기본값

하나의 <strong>주장 또는 질문</strong>을 세우고, 뉴스를 그 논증의 근거로 인용합니다.

구조:

1. 훅 — 주장/질문을 던진다 ("X는 사실 Y다", "왜 지금 모두 Z로 가는가?")
2. 근거 — 뉴스/사실 1~3건을 인용해 주장을 뒷받침 (출처 명시, 내부링크)
3. 해석 — Tom의 읽기: 이 사실들이 무엇을 의미하는지, 다른 사건과 어떻게 연결되는지
4. 반론/한계 — 솔직하게 ("이렇게 볼 수도 있지만…")
5. 결론 — 독자(특히 한국 개발자)에게 구체적으로 무엇을 뜻하는가

모범 사례: [[2026-04-01-cognitive-dark-forest]], [[2026-04-27-swe-bench-limitations]], [[2026-05-06-claude-code-k-shaped-productivity]]

### 2. 종합 다이제스트 (synthesis digest)

여러 소식을 <strong>하나의 흐름/내러티브</strong>로 엮습니다. 개별 요약의 나열이 아니라, "이번 주/이 흐름의 큰 그림 + 내 해석".

규칙: 각 항목은 짧게, 그리고 <strong>반드시 해당 주제의 기존 단독 글로 내부링크</strong>(hub-and-spoke). 다이제스트는 연결·추세만 더하고, 사실 재서술은 최소화.

모범 사례: [[2026-02-19-january-2026-ai-roundup]] (단, 항목 재요약을 줄이고 연결 분석을 늘릴 것)

### 3. 비교/평가 프레임워크 (comparison framework)

<strong>내가 만든 기준(축)</strong>으로 도구·모델을 줄세웁니다. 에버그린이라 검색 유입·재방문이 높음.

규칙: 비교축은 Tom이 정의(가격/속도/한국어/생태계 등), 표·기준은 내 것, 출처는 수치 근거로만 인용. 정기적으로 `updatedAt` 갱신.

모범 사례: [[2026-02-19-ai-coding-tools-pricing-2026]], [[2026-02-19-ai-model-comparison-2026]]

## 금지 패턴 (이게 "2차 가공"의 정체)

- ❌ 출처 한 건을 처음부터 끝까지 순서대로 한국어로 풀어쓰기
- ❌ 출처의 목차/구조를 그대로 따라가는 헤딩 구성
- ❌ 안 써본 것에 "제가 직접 써보니" 같은 가짜 경험 (날조 금지)
- ❌ 마지막에 붙이는 일반론적 "제 생각/총평" ("업데이트 추천합니다", "패러다임을 바꾼다" 류)
- ❌ 단일 출처만 인용 (가능하면 2개 이상 + 블로그 기존 글 내부링크)

## 권장 패턴

- ✅ 첫 문장부터 내 주장/질문이 보인다 (출처 소개가 아니라)
- ✅ 출처는 "근거"로 인용하고 출처명·링크를 명시 ("Anthropic 발표에 따르면…")
- ✅ 최소 1개의 기존 블로그 글로 내부링크 (맥락·연속성)
- ✅ "한국 개발자에게 이게 왜 중요한가"를 한 단락 (의견으로, 사실 날조 없이)
- ✅ 솔직한 판단/반론 (확신 없으면 없다고)
