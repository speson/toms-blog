안녕하세요, Tom입니다.

"비밀번호 좀 만들어줘"라고 Claude에게 부탁해본 적 있으신가요? 그럼 아마 이런 비밀번호가 나왔을 겁니다:

```
G7$kL9#mQ2&xP4!w
```

KeePass 같은 비밀번호 관리 도구에 넣으면 <strong>"약 100비트 엔트로피, 매우 강력"</strong>이라고 나옵니다. 슈퍼컴퓨터로도 수십억 년 걸릴 것 같죠?

<strong>실제로는 27비트밖에 안 됩니다.</strong> 일반 컴퓨터로 <strong>몇 초 만에 뚫릴 수 있는</strong> 약한 비밀번호예요.

## 실험: LLM에게 비밀번호 50번 생성시켜보니

보안 회사 <strong>Irregular</strong>가 재밌는 실험을 했습니다.

<strong>실험 방법:</strong>

- Claude Opus 4.6, ChatGPT, Gemini에게 각각
- "비밀번호를 생성해줘" 요청을 <strong>50번 반복</strong>
- 온도(temperature)를 0.0~1.0으로 바꿔가며 테스트

<strong>결과:</strong>

| 모델 | 동일 비밀번호 반복 | 고유 비밀번호 수 | 선호 패턴 |
| ----------- | ------------------ | ---------------- | ------------------------ |
| Claude Opus | 18번/50번 (36%) | 30개 | 'G'로 시작 + 두 번째 '7' |
| ChatGPT | - | - | 'v'로 시작 |
| Gemini | - | - | 'k' 또는 'K'로 시작 |

<strong>가장 충격적인 사실:</strong>

- 온도를 <strong>0.0으로 설정</strong>하면 → <strong>50번 전부 똑같은 비밀번호</strong>
- 온도를 1.0으로 올려도 → <strong>패턴은 여전히 존재</strong>

## 엔트로피 착시 현상

<strong>KeePass 평가:</strong> "100비트 엔트로피, 매우 강력" 
<strong>실제 Shannon 엔트로피:</strong> <strong>27비트</strong>

왜 이런 차이가 날까요?

### 진짜 강력한 비밀번호의 조건

<strong>CSPRNG (암호학적으로 안전한 난수 생성기):</strong>

```python
import secrets
password = secrets.token_urlsafe(16)
# 결과: 'Dg3K_8xNm2pQ7vL9'
# 모든 문자가 균등한 확률로 선택됨
```

<strong>LLM:</strong>

```python
# "비밀번호 생성해줘"
# 결과: 'G7$kL9#mQ2&xP4!w'
# 15번째 자리가 숫자 '2'일 확률 99.7% (거의 고정)
```

LLM은 <strong>"가장 그럴듯한 다음 토큰"</strong>을 예측하도록 훈련되었습니다. 즉, <strong>예측 가능성을 극대화</strong>하는 게 목표예요.

이건 비밀번호 생성과 <strong>정반대</strong>입니다.

## 더 위험한 문제: AI 코딩 에이전트

여기서 끝이 아닙니다. 더 큰 문제는 <strong>AI 코딩 도구가 코드에 취약한 비밀번호를 하드코딩</strong>한다는 점입니다.

<strong>실제 사례:</strong>

```python
# Claude Code가 생성한 코드
DATABASE_PASSWORD = "K7#mP9vL2$xQ4!w"
```

```javascript
// Codex가 생성한 코드
const API_KEY = "k9#vLmP7$Q2&xW4!";
```

<strong>문제점:</strong>

1. <strong>"비밀번호 생성해줘"</strong> → `openssl rand` 같은 안전한 방법 제안 
 올바른 접근

2. <strong>"비밀번호 추천해줘"</strong> → LLM이 만든 패턴 비밀번호 바로 삽입 
 위험한 접근

실제로 GitHub에서 `K7#mP9`, `k9#vL` 같은 패턴을 검색하면 <strong>이미 수많은 저장소에서 발견</strong>됩니다.

## 왜 LLM은 비밀번호 생성에 부적합한가?

<strong>근본적인 구조 문제:</strong>

| 특성 | CSPRNG | LLM |
| -------- | -------------------- | --------------------------- |
| 목표 | 예측 불가능성 극대화 | 그럴듯함 극대화 |
| 무작위성 | 완전 균등 분포 | 편향된 분포 |
| 엔트로피 | 실제 100비트 | 겉보기 100비트, 실제 27비트 |
| 보안성 | 암호학적으로 안전 | 구조적으로 취약 |

<strong>Irregular의 결론:</strong>

> "프롬프트를 잘 짜거나 온도를 조절해도 근본적으로 해결 불가능합니다."

## 개발자가 해야 할 일

### 하지 말아야 할 것

```python
# AI에게 "비밀번호 추천해줘" 요청

```

### 해야 할 것

```python

import secrets
password = secrets.token_urlsafe(32)

# Node.js
const crypto = require('crypto');
const password = crypto.randomBytes(32).toString('base64');

# CLI
openssl rand -base64 32
```

### AI 코딩 도구 사용 시 주의사항

1. <strong>코드 리뷰 필수</strong> — AI가 생성한 비밀번호/API 키는 반드시 검증
2. <strong>환경 변수 사용</strong> — 하드코딩된 비밀번호 절대 금지
3. <strong>비밀 관리 도구 활용</strong> — 1Password, Vault, AWS Secrets Manager 등

## 마무리하며

LLM은 정말 많은 것을 잘합니다. 하지만 <strong>비밀번호 생성은 그중 하나가 아닙니다.</strong>

문제는 겉보기엔 강력해 보인다는 점입니다. KeePass도 속고, 사람도 속고, 심지어 개발자도 속습니다.

<strong>핵심은 이것입니다:</strong>

- 진짜 보안은 <strong>외형이 아니라 실제 엔트로피</strong>에 달려 있습니다
- LLM의 <strong>예측 중심 설계</strong>는 비밀번호 생성과 근본적으로 맞지 않습니다
- AI 코딩 도구가 코드에 심은 취약한 비밀번호는 <strong>은밀하게 퍼질 수 있습니다</strong>

혹시 여러분 프로젝트에 AI가 생성한 비밀번호가 하드코딩되어 있진 않나요? 한 번 확인해보시는 걸 추천합니다.
